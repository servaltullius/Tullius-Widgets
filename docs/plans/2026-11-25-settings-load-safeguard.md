그 상태로 사용자가 설정을 바꾸자 기본값에서 시작한 설정이 원래 파일을 덮어썼다. 슬롯 1과 도로롱 아이콘, 켜 둔 위젯 설정이 사라졌고, 백업은 없었다.

**확인된 것**
- 파일 안의 저장 번호(rev)가 이번 실행의 저장 횟수와 같은 13이었다. 화면이 받은 파일의 저장 번호를 이어받지 않았다는 뜻이다.
- 지금 빌드는 정상 파일을 제대로 읽는다. 브라우저에서 확인했고, 13:57 게임 실행에서도 확인했다.

**모르는 것**
- 오늘 아침에 쓰인 파일을 받아들이지 못한 이유. 그 파일이 없고, 게임 안 화면의 콘솔 기록도 없다.

원인을 모르므로, 원인이 무엇이든 데이터를 잃지 않게 막고, 다음에 생기면 원인을 알 수 있게 기록을 남긴다.

## 완료 조건과 검증

1. **덮어쓰기 전 백업 (플러그인)**
   - 저장할 때 디스크의 기존 파일이 아래 중 하나면, 쓰기 전에 기존 파일을 `TulliusWidgets.json.unloaded-<YYYYMMDD-HHMMSS>.bak`로 복사한다.
     - 저장 번호가 새로 저장하는 번호보다 크거나 같다. 화면이 그 파일을 이어받지 않았다는 뜻이다.
     - 저장 번호를 읽을 수 없다(깨진 파일, 예전 형식).
   - v1.1.8 이전 형식(저장 번호가 없지만 올바른 설정 파일)은 백업만 남기고, 4번 안내는 띄우지 않는다. 화면이 이 형식을 정상적으로 읽기 때문이다.
   - 두 저장 번호를 넣어 경고 로그를 남긴다.
   - 이런 백업은 최신 5개만 남긴다.
   - 검증: 네이티브 테스트(임시 폴더)로 다음을 확인한다.
     - 저장 번호가 커지면 복사하지 않는다.
     - 같거나 작거나 읽을 수 없으면 복사하고, 복사본 내용이 원본과 같다.
     - 파일이 없으면 아무것도 하지 않는다.
     - 6개째가 생기면 가장 오래된 것이 지워진다.
2. **게임 시작 시점 사본 (플러그인)**
   - 게임을 켠 뒤 처음 저장할 때 기존 파일을 `TulliusWidgets.json.prev`로 복사한다(이전 `.prev`는 바꿈).
   - 검증: 네이티브 테스트로 첫 저장에서만 복사되는지 확인한다.
3. **불러오기 실패 기록 (화면 → 플러그인)**
   - 받은 설정을 해석하지 못하면(JSON 오류, 객체 아님, 병합 중 예외) 화면이 이유를 플러그인에 보내고, 플러그인이 경고 로그로 남긴다.
   - 검증: vitest(실패 이유가 브리지로 전달됨), 계약 테스트(리스너 등록과 로그).
   - 게임에서는 일부러 깨뜨린 파일로 로그 한 줄이 남는지 확인한다.
4. **패널 안내 (플러그인 → 화면)**
   - 1번 백업이 생기면 플러그인이 화면에 알리고, 설정 창에 안내를 띄운다. 안내에는 백업 파일 이름과 되돌리는 방법을 적는다.
   - 안내는 닫을 수 있다.
   - 검증: vitest와 브라우저 확인. 게임에서는 저장 번호를 크게 고친 파일로 확인한다.
5. **문서**
   - README에 백업 파일 위치(MO2는 overwrite 폴더)와 되돌리는 방법(게임을 끄고 이름 바꾸기)을 적는다.

## 검수(/code-review) 반영 (2026-11-25)

- 같은 초에 생긴 백업의 번호를 `_02` 꼴로 바꿨다. 이제 이름 순서가 만든 순서와 같다. 정리할 때 방금 만든 백업은 지우지 않는다. 시계가 뒤로 간 경우에 대비한 것이다.
- 기존 파일을 열 수 없으면(다른 프로그램이 잠깐 잡고 있는 경우 등) 50ms 뒤 한 번 더 읽는다. 그래도 안 되면 백업과 실패 안내 없이 로그만 남긴다. 읽지 못한 것이 화면의 실패라는 근거가 없기 때문이다.
- 화면이 저장된 설정을 읽지 못하면 그 즉시 화면 위쪽과 설정 창에 안내를 띄운다. 안내에는 아무것도 바꾸지 않으면 파일이 그대로라는 것을 적는다.
  - 이후 저장으로 백업이 생기면 안내를 백업 파일 이름으로 바꾼다.
  - 같은 게임 중에 저장된 설정을 다시 받아 제대로 읽으면, 백업이 없는 실패 안내는 거둔다.
- 로그에 남기는 실패 이유는 UTF-8 문자를 쪼개지 않게 자른다.
- 알림 스크립트를 만드는 부분과 로그 자르기를 함수로 빼서 네이티브 테스트로 확인한다.
- 2026-11-25 사용자 인게임 확인(DLL md5 `50a9efac119d0dd1ad102a88565ddf4e`): 정상 파일로 켜서 설정을 바꿨을 때 `.prev`만 생기고 `.unloaded…bak`, 경고 로그, 안내는 없었다.

## Codex 커밋 전 교차 검토 반영 (2026-11-25)

원문은 세션 scratchpad의 `codex-safeguard-packet.txt.codex-20261125-164715.md`에 있다(files 모드, 559초, 파일 변경 없음).

**판정 방식 교체.** 저장 번호만 비교하면 0.2초 안의 변경이 한 번에 저장될 때 번호가 건너뛰어 놓치고, 병합에 실패해도 번호를 이미 받아들인 것으로 셌다. 그래서 판정 방식을 바꿨다.
- 화면은 저장할 때마다 이번 게임에서 받아들인 설정 파일과 그 번호(`loadedFile`, `loadedRev`)를 함께 보낸다.
- 플러그인은 기존 파일의 번호가 화면이 받아들인 번호이거나 이번 게임에서 자기가 쓴 번호일 때만 "이어서 저장"으로 본다. 그 밖에는 백업한다.
- 이 필드가 없는 예전 화면은 기존의 번호 비교로 판정한다.

**반영**
- 백업이 필요한데 만들지 못하거나, 기존 파일을 확인할 수 없으면(존재 확인 오류, 두 번 읽어도 실패) 저장을 거부한다. 0.2초 뒤 한 번 더 확인하고, 그래도 안 되면 화면에 저장 실패를 돌려준다.
- 쓰기에 실패하면 쓰기만 한 번 더 시도한다. 백업 안내는 쓰기가 성공한 뒤에만 보낸다.
- `.prev` 표시는 복사에 성공했을 때만(또는 파일이 없을 때) 이번 게임에서 끝난 것으로 친다.
- 읽기에 실패한 동안에는 설정 창을 여는 것만으로 "첫 실행 안내 봤음"을 저장하지 않는다.
- 저장 파일을 새로 받으면 그 전에 예약된 저장을 취소한다.
- 받은 설정을 적용하다 실패하면 저장 번호를 원래대로 되돌린다.
- 빈 파일, 너무 큰 파일, 열 수 없는 파일은 플러그인이 화면에 알려 바로 안내한다. 파일 맨 앞의 UTF-8 BOM은 화면에 보내기 전에 지운다.
- 백업 정리
  - 폴더를 오류 코드로 순회해 예외가 나지 않게 했다.
  - 이 코드가 만든 이름 형식만 정리 대상으로 삼는다.
  - 삭제에 성공한 것만 센다.
  - 같은 초 번호가 99까지 다 차면 복사 실패로 처리한다.
- 저장 스레드가 쓰는 상태를 스레드보다 먼저 선언했다. 종료할 때 스레드보다 늦게 정리된다.
- 확인용으로 읽는 양을 처음에 잰 크기로 제한한다.
- 이미 설정을 쓰는 중에 다시 받은 파일을 읽지 못하면 실패 안내를 띄우지 않는다.
- 안내와 README
  - MO2 위치는 "보통 overwrite, Data 탭에서 확인"으로 고쳤다.
  - `.prev`가 언제 바뀌는지를 바로잡았다.
  - 손상된 파일의 백업은 그대로 쓸 수 없을 수 있다고 적었다.
  - 저장을 거부할 수 있다는 것을 적었다.
- 드롭다운
  - 단축키 입력을 기다리는 동안에는 메뉴가 키를 받지 않는다.
  - 표시 위치를 값으로 기억해, 목록이 바뀌어도 같은 항목을 가리킨다.
  - 키를 누를 때마다 표시된 항목이 보이게 스크롤한다.

**보류**
- 백업 안내가 다른 저장의 응답에 붙는 경쟁: 정상 흐름에서는 생기지 않는다.
- 파일을 바꾸는 예비 경로와 게임 쪽 읽기의 경쟁: 기존 동작이다.
- 시계를 되돌린 뒤 두 번째 백업의 정리 순서.
- Home/End를 게임 단축키로 지정한 경우: 메뉴 상태를 플러그인에 전달해야 한다.
- 메뉴를 닫은 뒤 포커스가 돌아갈 위치.
- 서로 다른 Esc 두 번이 하나로 합쳐지는 경우: 기존 Esc 처리의 문제다.

**반대**
- 유효한 JSON의 일부 값이 빠지는 것을 감지하지 못함: 예전 형식을 옮기려면 이 동작이 필요하다.
- 저장 번호가 uint32를 넘는 경우: 사실상 생기지 않는다.
- aria 역할: Ultralight에는 화면 낭독기가 없다.
- 위젯 선택 중 닫힌 드롭다운에서 방향키가 위젯을 움직임: 지난 검수에서 의도한 동작으로 정했다.
- 2026-11-25 사용자 인게임 확인(DLL md5 `64ad84f0f908202a0162e15a83be23f4`): 정상 파일(rev 14)로 켜서 설정을 바꾸자 두 번 저장됐다. 첫 저장 때 `.prev`(rev 14)만 생겼고, 저장된 파일은 `rev 16, loadedFile true, loadedRev 14`였다. 두 번째 저장은 플러그인이 직전에 쓴 번호를 이어받아 백업 없이 저장됐다. `.unloaded…bak`, 경고, 저장 거부는 없었다.
